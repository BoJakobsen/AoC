whole DSL; the clauses actually used:

Things worth internalising:

Deconstruction works at many levels, which is very handy

*Multiple =for= clauses iterate in parallel, not nested.* They stop at
the shortest. This is how [[file:AoC2025/src_lisp/puz_06.el][2025 puz_06]] walks an operator list and an
operand list together, and how [[file:AoC2025/src_lisp/puz_06.el][2025 puz_06 part 1]] walked five rows at once:

#+begin_src emacs-lisp
(cl-loop for op in ops
         for x  in operand-lists
         sum (apply (intern-soft op) x))
#+end_src

*Named accumulators let one pass compute both puzzle parts.* From
[[file:AoC2025/src_lisp/puz_02.el][2025 puz_02]] — one scan of the range, two sums:

#+begin_src emacs-lisp
(cl-loop for num from low to high
         for s = (number-to-string num)
         when (string-match-p puz-rx-doubled s)      sum num into part1
         when (string-match-p puz-rx-two-or-more s)  sum num into part2
         finally return (list part1 part2))
#+end_src

Gotcha: =count= counts *true results of its own expression*, it does not
just tick per iteration — =when COND count EXPR= counts passes where both
are true. See =puz-solve-part1d= in [[file:AoC2025/src_lisp/puz_04.el][2025 puz_04]].

Example of standard "loop over pairs", also using deconstruction 
#+begin_src emacs-lisp   
  (cl-loop for ((a1 b1) . rest) on parsed
           when rest
           maximize (cl-loop
                     for (a2 b2) in rest
                     maximize  (* (1+ (abs (- a1 a2)))(1+ (abs (- b1 b2))))))

#+end_src

=cl-labels= vs =let=: a =let=-bound lambda cannot easily call itself (the
name isn't in scope inside its own body). =cl-labels= binds real function
names that *are* visible inside each other — that is what makes the
closure factory in [[file:AoC2025/src_lisp/puz_11.el][2025 puz_11]] possible.

* apply, funcall and dynamic function names

Three separate tricks that all showed up in [[file:AoC2025/src_lisp/puz_06.el][2025 puz_06]]:

*String → function.* =(intern-soft "max")= returns the symbol =max= if it
already exists (=intern= would create it — =intern-soft= is the safe one
for untrusted input; it returns =nil= for unknown names).

#+begin_src emacs-lisp
(funcall (intern-soft op) a b c d)      ; op is the string "max"
(apply (intern-soft op) list-of-args)   ; args in a list
#+end_src

*Transpose via apply + cl-mapcar.* The lisp equivalent of Python's
=zip(*rows)=:

#+begin_src emacs-lisp
(apply #'cl-mapcar #'list rows)     ; list of rows -> list of columns
(apply #'cl-mapcar #'string rows)   ; rows of chars -> columns as *strings*
#+end_src

The second form is the neat one: =#'string= builds a string from
characters, so a list of strings becomes a list of column-strings in one
call. Reading a grid column-wise for free.

*apply has an argument limit.* =(apply #'+ list)= is fine for a few
hundred elements but blows past =max-args= for big lists; =(cl-reduce #'+
list)= folds pairwise instead and has no limit. Noted in [[file:AoC2025/src_lisp/puz_06.el][2025 puz_06]] when
going from =apply #'+= to =cl-reduce #'+=.

* rx: groups and back-references

[[file:AoC2025/src_lisp/puz_02.el][2025 puz_02]] needed "digits that are some block repeated" — a back-reference
problem:

#+begin_src emacs-lisp
(rx bos (group (one-or-more digit)) (backref 1) eos)              ; exactly twice
(rx bos (group (one-or-more digit)) (one-or-more (backref 1)) eos) ; two or more
#+end_src

Points:
- =(group ...)= is a numbered capture group; =(backref N)= matches whatever
  group N matched. Groups are numbered by opening order, from 1.
- =bos= / =eos= = beginning/end of *string*; =bol= / =eol= = beginning/end of
  *line*. For whole-string validation, =bos=/=eos= is what you want — with
  =bol=/=eol= a multi-line string can match on any single line.
- =string-match-p= is the side-effect-free variant: no =match-data= is set,
  so it is both faster and safer than =string-match= when you only need
  yes/no.
- Building the regexp once with =defconst= keeps it out of the inner loop
  (=rx= is a macro, so it is expanded at compile time either way — but a
  named constant documents the intent).

* Vectors, sequences and in-place mutation

Elisp vectors are fixed-length, O(1)-indexed, and *mutable* — the closest
thing to a numpy array for grid work.

| Operation                 | Function                         |
|---------------------------+----------------------------------|
| Build from string/list    | =(vconcat "abc")= → =[?a ?b ?c]= |
| Read element              | =(aref v i)=                     |
| Write element (in place!) | =(aset v i val)=                 |
| Length                    | =(length v)=                     |
| Slice                     | =(seq-subseq v start end)=       |
| Take n elements           | =(take list n)=                  |
| Max element               | =(seq-max v)=                    |
| Index of element          | =(seq-position v val)=           |
| Any element satisfies?    | =(seq-some PRED seq)=            |
| Fold                      | =(seq-reduce FN seq init)=       |

=vconcat= on a buffer string is the cheapest way to get a whole grid into
a random-access array — [[file:AoC2025/src_lisp/puz_04.el][2025 puz_04]] uses =(vconcat (buffer-string))= and then
does the whole erosion simulation with =aref= / =aset=.

Horner's method as a one-liner fold, from [[file:AoC2025/src_lisp/puz_03.el][2025 puz_03]] — digits to number:

#+begin_src emacs-lisp
(seq-reduce (lambda (a b) (+ (* 10 a) b)) vec 0)
#+end_src

Destructive vs. non-destructive: =nreverse= reuses the cons cells (fast,
but the input list is garbage afterwards), =reverse= copies. =push= +
=nreverse= is the standard accumulate-and-fix-order pair. Using =nreverse=
on a list you still need later is a classic self-inflicted bug — [[file:AoC2025/src_lisp/puz_06.el][2025 puz_06]]
was refactored from =(nreverse parsed)= + =pop= to =last= / =butlast=
precisely to stop mutating the parsed input.

* Sorting with keys (Emacs 30 calling convention)

#+begin_src emacs-lisp
  (sort list :key #'car)                 ; new keyword style, Emacs 30+
  (sort list :reverse t)
  (sort list :key #'car :lessp #'<)      ; explicit comparator
  (sort list (lambda (a b) (< (car a) (car b))))   ; old style, still works
#+end_src

Used in [[file:AoC2025/src_lisp/puz_05.el][2025 puz_05]] to sort intervals by start before merging. The =:key=
form is much closer to Python's =sorted(xs, key=...)= and avoids writing
the comparator by hand. Note =sort= may destructively reuse the input.

* Interval merging as a fold

A pattern worth remembering beyond AoC — from [[file:AoC2025/src_lisp/puz_05.el][2025 puz_05]]. Once the list is
sorted by start, overlap testing collapses to a single comparison, and
the whole merge is a =seq-reduce= where the accumulator is the merged list
built backwards:

#+begin_src emacs-lisp
(defun puz-merge-into (merged next)
  (let ((prev (car merged)))
    (if (<= (car next) (cadr prev))                       ; overlap (sorted!)
        (cons (list (car prev) (max (cadr prev) (cadr next))) (cdr merged))
      (cons next merged))))

(seq-reduce #'puz-merge-into rest (list first))
#+end_src

The general overlap test is =a1 <= b2 && b1 <= a2=; sorting first reduces
it to one half. Returning a *new* accumulator each step (=cons= onto the
tail) rather than =push=/=pop= on a mutable local is what makes it read as
a clean fold.

* Hash tables and memoization

#+begin_src emacs-lisp
(make-hash-table :test 'equal)   ; 'equal for strings/lists, 'eq for symbols
(gethash KEY TABLE)              ; nil if absent
(puthash KEY VAL TABLE)          ; *returns VAL* — this is the useful bit
#+end_src

*The memo idiom.* Because =puthash= returns the stored value and =or=
short-circuits, a whole memoized recursion fits in one expression
([[file:AoC2025/src_lisp/puz_11.el][2025 puz_11]], =puz-dfs-count3=):

#+begin_src emacs-lisp
(defun puz-dfs-count (state target)
  (if (equal state target)
      1
    (or (gethash state puz-cache)                    ; hit: done
        (puthash state                               ; miss: compute and store
                 (cl-loop for next in (gethash state puz-dat)
                          sum (puz-dfs-count next target))
                 puz-cache))))
#+end_src

This is elisp's answer to Python's =@cache= — there is no decorator, so the
lookup/store is explicit, but the =or= + =puthash= pair keeps it to two
lines. Caveat: it caches =nil= badly (a genuinely-nil result looks like a
miss), fine when the values are numbers.

*Cache key design.* Keying on =(list state target)= works but is
redundant when =target= is fixed for a whole run — a fresh table per target
is smaller and faster. Two ways to get that, both in [[file:AoC2025/src_lisp/puz_11.el][2025 puz_11]]:

1. /Dynamic binding/ — =defvar= the cache (making it special), then =let=-bind
   a fresh table around the call. The recursive function just refers to
   the global name and picks up the binding. Classic lisp, but the
   function's contract is now invisible in its signature.
2. /Closure factory/ — return a function that has captured its own private
   cache:

#+begin_src emacs-lisp
(defun puz-make-counter (target)
  (let ((cache (make-hash-table :test 'equal)))
    (cl-labels ((countit (state)
                  (if (equal state target) 1
                    (or (gethash state cache)
                        (puthash state
                                 (cl-loop for next in (gethash state puz-dat)
                                          sum (countit next))
                                 cache)))))
      #'countit)))

(funcall (puz-make-counter "out") "you")
#+end_src

The second is the properly functional one: no globals, cache lifetime tied
to the returned function, and =cl-labels= makes the inner recursion legal.
Requires lexical binding (it is a real closure).

* Buffer as a grid — position arithmetic

The trick that made [[file:AoC2025/src_lisp/puz_04.el][2025 puz_04]] fast: don't convert to (row, col). A buffer
line of =n-cols= characters plus its newline has *stride* =n-cols + 1=, so
the eight neighbours of any position are eight fixed integer offsets,
precomputed once ([[file:helper_functions/aoc-functions.el][aoc-functions.el]], =puz-grid-init=):

#+begin_src emacs-lisp
(let ((stride (1+ n-cols)))
  (list (- -1 stride) (- stride) (- 1 stride)
        -1                       1
        (+ stride -1) stride     (+ stride 1)))
#+end_src

Then neighbour counting is just =(char-after (+ pos offset))=. =char-after=
returns =nil= outside the buffer, so top/bottom edges self-handle; the
newline character handles left/right edges (a neighbour that wraps lands
on =?\n=, which is never a target char). No bounds checking at all.

The =&rest= + =memq= combination makes "count any of these chars" free:

#+begin_src emacs-lisp
(defun puz-grid-count-nab (pos &rest target)
  (let ((acc 0))
    (dolist (offset puz-grid-offsets)
      (when (memq (char-after (+ pos offset)) target)
        (cl-incf acc)))
    acc))
#+end_src

=memq= (=eq= test) is right here because characters are integers — for
strings or lists it would have to be =member= (=equal= test).

* Buffer mutation primitives

| Want                            | Use                                         |
|---------------------------------+---------------------------------------------|
| Replace char at POS             | =goto-char=, =delete-char 1=, =insert-char= |
| Bulk char replacement in region | =(subst-char-in-region BEG END FROM TO t)=  |
| Disable undo recording (speed)  | =(let ((buffer-undo-list t)) ...)=          |
| Rectangle text                  | =extract-rectangle=, =rectangle-mark-mode=  |

The =buffer-undo-list= trick is significant: without it, every
=delete-char= / =insert-char= in a mutation loop records an undo entry, and
on a large grid that dominates the runtime.

The rectangle approach (=rectangle-mark-mode= + =extract-rectangle= to grab
a 3x3 neighbourhood) was the *first* thing tried and is ~40x slower than
offset arithmetic — nice demonstration that "use the editor's own
commands" is not always the right instinct for compute.

* Two-phase in-place updates

[[file:AoC2025/src_lisp/puz_04.el][2025 puz_04]] part 2 is a cellular-automaton style erosion: all cells must be
evaluated against the *same* generation. Three ways to avoid reading your
own writes, all present in the file:

1. Write a sentinel char (=?X=) instead of the final value, so the count
   function can still see "was @ this generation" via =(memq c '(?@ ?X))=,
   then sweep the whole grid converting =?X= → =?.=.
2. Same, but remember the changed positions in a list (=push=) and only fix
   those up afterwards — one pass instead of a second full sweep.
3. Copy the grid.

Option 2 is the one that survived (=puz-remove-rolls-vec2=). Generally
useful for any simulate-a-generation problem.

* Performance tooling

| Tool                                                  | Use                                |
|-------------------------------------------------------+------------------------------------|
| =(benchmark-run N FORM)=                              | → =(seconds gcs gc-seconds)=       |
| =(benchmark-call FN N)=                               | same, for a function value         |
| =(profiler-start 'cpu)= … =(profiler-report)=         | sampling profiler, tree output     |
| =(byte-compile 'symbol)= / =byte-compile-file=        | compile a single function / a file |
| =(subr-native-elisp-p f)=, =(byte-code-function-p f)= | check what a symbol actually is    |

The headline lesson from [[file:AoC2025/src_lisp/puz_04.el][2025 puz_04]]'s benchmark block: *byte-compiling is
worth 4–10x*, and it also makes the profiler readable. Interpreted code
profiles as a tree of =let= / =while= / =if= primitives — the interpreter's
own machinery — which tells you nothing. Byte-compiled, the profile
collapses to the actual functions, and it became immediately obvious that
81% of the time was in the neighbour counter.

Helpers in [[file:helper_functions/aoc-functions.el][aoc-functions.el]]: =puz-compile-all=, =puz-compilation-status=,
=puz-benchmark= — all built on =mapatoms= (see below).

* Namespace management with mapatoms

=mapatoms= walks *every interned symbol* in the obarray. Combined with a
naming prefix it gives a poor-man's namespace teardown ([[file:helper_functions/aoc-functions.el][aoc-functions.el]]):

#+begin_src emacs-lisp
(mapatoms
 (lambda (sym)
   (when (string-prefix-p "puz-" (symbol-name sym))
     (when (boundp sym)  (makunbound sym))     ; kill variable value
     (when (fboundp sym) (fmakunbound sym))))) ; kill function definition
#+end_src

Related: =(unload-feature 'FEATURE t)= undoes a =require= (the =t= forces it
even when other code depends on it). Essential during interactive
development, because =require= is *idempotent* — re-evaluating
=(require 'aoc-functions)= after editing the library does *nothing*. To
pick up changes: =unload-feature=, or just =load-file= the library directly.

A symbol has independent variable and function slots — =boundp= /
=makunbound= for one, =fboundp= / =fmakunbound= for the other. This is why
=(let ((op #'+)) (op a b))= fails but =(funcall op a b)= works.

* Locating files relative to the source file

Loading a sibling helper directory, without hard-coded absolute paths:

#+begin_src emacs-lisp
(add-to-list 'load-path
             (expand-file-name "../../helper_functions"
                               (file-name-directory
                                (or load-file-name buffer-file-name))))
#+end_src

- =load-file-name= is bound while a file is being =load=ed — =nil= when you
  are just evaluating a form with =C-x C-e= in a buffer.
- =buffer-file-name= is the fallback for interactive evaluation.
- The =or= makes the same line work both ways. Note neither is bound
  inside a =defun= at call time — this must run at top level.

* Macros — the one that bit

[[file:helper_functions/aoc-functions.el][aoc-functions.el]] defines =puz-loaders= to generate the two per-day loader
functions:

#+begin_src emacs-lisp
(defmacro puz-loaders (path day)
  `(defun puz-load-data () ...)        ; <- discarded!
  `(defun puz-load-testdata () ...))   ; <- only this is returned
#+end_src

*A macro body is an ordinary function body: it returns its last form.*
Two backquoted forms in sequence means the first is evaluated (producing
a list, which is thrown away) and only the second becomes the expansion.
Verified — after =(puz-loaders "../data" 6)=, =puz-load-testdata= is defined
and =puz-load-data= is not. The fix is to return a single form:

#+begin_src emacs-lisp
(defmacro puz-loaders (path day)
  `(progn
     (defun puz-load-data () (puz-load ,(concat path (format "/%02d_data.dat" day))))
     (defun puz-load-testdata () (puz-load ,(concat path (format "/%02d_testdata.dat" day))))))
#+end_src

Debugging aid: =(macroexpand '(puz-loaders "../data" 6))= shows exactly what
the macro produces — always look at the expansion before believing a macro.

Backquote recap: =`= quotes the template, =,= evaluates and splices in a
single value, =,@= splices a *list* of forms. Here =,(concat ...)= runs at
expansion time, so the path is baked into the generated function as a
literal string.

* Small things worth remembering

- =(split-string s "" t)= explodes a string into single-character strings —
  handy but wasteful; =(vconcat s)= or =(string-to-list s)= is usually better
  ([[file:AoC2025/src_lisp/puz_03.el][2025 puz_03]] notes this).
- =(split-string s)= with no separator splits on whitespace *and* trims —
  exactly right for whitespace-separated number rows ([[file:AoC2025/src_lisp/puz_06.el][2025 puz_06]]).
- =(split-string text "\n\n" t)= splits an input file into its blank-line
  separated blocks ([[file:AoC2025/src_lisp/puz_05.el][2025 puz_05]]) — the elisp equivalent of Python's
  =f.read().split('\n\n')=.
- =last= returns the last *cons*, so =(car (last lst))= is the last element;
  =butlast= returns everything but the last. Non-destructive pair, unlike
  =nreverse= + =pop= ([[file:AoC2025/src_lisp/puz_06.el][2025 puz_06]]).
- =unless= returns =nil= when the condition holds, which makes it a free
  base case for list-building recursion — =(cons x (recurse ...))= against a
  =nil= tail just works ([[file:AoC2025/src_lisp/puz_03.el][2025 puz_03]], =puz-construct-largest=).
- =(mapconcat #'identity list "")= joins strings; since Emacs 29 the
  separator is optional and =identity= can be omitted for a list of strings.
- =(message "%S" x)= prints the *readable* form (strings get quotes);
  =%s= prints the display form. =%S= is what you want when checking parsed
  data structures.
- =(number-to-string n)= / =(string-to-number s)= — remember the latter
  returns =0= on garbage rather than signalling.
- =seq-some= returns the first non-nil *result of the predicate*, not =t= —
  usable as "find" as well as "any" ([[file:AoC2025/src_lisp/puz_05.el][2025 puz_05]]).

** pcase — pattern matching as dispatch and as parser

Two quite different uses turned up.

*Dispatch on a value* ([[file:AoC2024/src_lisp/puz_17.el][2024 puz_17]], the opcode switch). Numbers,
strings and keywords match themselves, clauses are tried top to bottom:

#+begin_src emacs-lisp
(pcase (puz-get-op cpu)
  (0 ...)
  ((and 3 (guard (not (zerop (puz-cpu-a cpu))))) ... 'jnz)  ; 3 AND a condition
  (3 nil)                                                   ; 3, guard failed
  (op (error "Bad opcode: %S" op)))                         ; catch-all, binds op
#+end_src

- =(and PAT (guard EXPR))= — pattern plus an arbitrary boolean. Order
  matters: the guarded clause has to come before the plain =3=.
- A *bare symbol is a binding, not a comparison*. =op= matches anything and
  binds it; =_= matches anything and binds nothing. Gotcha: to compare
  against the /value/ of a variable =x= you need =(pred (equal x))= (or
  =(guard (equal val x))=) — writing just =x= silently shadows it and
  matches everything.
- A quoted symbol ='jnz= matches that symbol literally.
- No clause matching → =pcase= returns =nil= (=pcase-exhaustive= signals
  instead).

*Destructure a string with rx* ([[file:AoC2025/src_lisp/puz_10.el][2025 puz_10]], the parser). Inside
=pcase=, an =(rx ...)= pattern may contain =(let VAR RX)=, which binds VAR to
that sub-match — named groups, no =match-string= bookkeeping:

#+begin_src emacs-lisp
(pcase line
  ((rx bol "[" (let lights (one-or-more (any ".#"))) "] "
       (let buttons (one-or-more ...))
       "{" (let joltage (one-or-more (any "," digit))) "}" eol)
   ...use lights, buttons, joltage as strings...))
#+end_src

Note a line that does not match just falls through silently (=nil=) —
nice for skipping blanks, nasty for hiding a parser bug. A final
=(_ (error "Bad line: %S" line))= clause makes it loud.

** cl-defstruct — records with setf-able accessors

[[file:AoC2024/src_lisp/puz_17.el][2024 puz_17]] keeps the whole CPU state in one struct:

#+begin_src emacs-lisp
(cl-defstruct puz-cpu
  "Docstring."
  (a 0) (b 0) (c 0) (pc 0) (out nil) prog)   ; (SLOT DEFAULT) or bare SLOT
#+end_src

That one form generates =make-puz-cpu= (keyword constructor, =:a 5 :prog
...=), one accessor per slot (=puz-cpu-a=, =puz-cpu-pc=, ...), the predicate
=puz-cpu-p= and =copy-puz-cpu= (shallow copy).

The key point: accessors are /generalized variables/ (places), so everything
that works on a place works on a slot:

#+begin_src emacs-lisp
(setf (puz-cpu-a cpu) (ash (puz-cpu-a cpu) -3))
(cl-incf (puz-cpu-pc cpu) 2)
(push val (puz-cpu-out cpu))
#+end_src

Structs are mutable and passed by reference, so =puz-exec-op= updates the
caller's cpu in place. They print readably as =#s(puz-cpu 0 0 0 ...)=, which
makes =(message "%S" cpu)= a decent debugger.

** Union-find (disjoint set) on vectors

[[file:AoC2025/src_lisp/puz_08.el][2025 puz_08]]. Two parallel vectors indexed by node number: =parent= and
=size=.

#+begin_src emacs-lisp
(vconcat (number-sequence 0 (1- n)))   ; parent[i] = i, every node its own root
(make-vector n 1)                      ; size[i] = 1
#+end_src

Because =aset= /returns the value it stored/, find-with-path-compression is
one expression — recurse to the root, write it back, return it:

#+begin_src emacs-lisp
(defun puz-find (dset i)
  (let ((parent (aref dset i)))
    (if (= i parent) i
      (aset dset i (puz-find dset parent)))))
#+end_src

Same trick as =puthash= in the memo idiom — =setf=, =aset=, =puthash= all
return the new value, so "store and return" never needs a =progn=.

trees shallow; returning the updated tree count from =puz-union= is what
lets part 2 stop with ~until (= 1 ...)~.

Small things: =number-sequence= is inclusive at both ends. =make-vector=
puts the /same/ object in every slot — fine for numbers, a trap if the
initial value is a list you later mutate.

** Flat vector as a 2D grid, coordinate compression, summed-area table

All from [[file:AoC2025/src_lisp/puz_09.el][2025 puz_09]] part 2.

*Flat grid.* One vector of =width * height=, and a single index helper
=(+ x (* y width))=. Neighbours are the offsets =-1 +1 -width +width=.
Unlike the buffer-as-grid trick there is no newline column acting as a
wall, so =±1= wraps from the end of one row to the start of the next. It
is harmless here only because the outermost ring is known to be empty —
otherwise pad the grid or check =x= explicitly.

*Coordinate compression.* Sort and de-duplicate the distinct x's (and
y's), then map coordinate → =2*rank + 1=. The odd cells are the real
coordinates, the even cells stand for the gaps between them (and the
border), so "is there space between these two lines" survives the
compression. Shrinks a ~100000² problem to a few hundred squared.

#+begin_src emacs-lisp
(mapcar #'seq-uniq (mapcar #'sort (apply #'cl-mapcar #'list points)))  ; -> (xs ys)
#+end_src

(transpose, sort each, uniq each — =seq-uniq= keeps order so sorted stays
sorted.)

*Flood fill with an explicit stack.* =push= / =pop= on a list is a LIFO
stack, so a =while stack= loop is an iterative DFS — no recursion depth
worries (=max-lisp-eval-depth=). Mark a cell when it is /pushed/, not when
it is popped, so nothing is queued twice.

*Summed-area table (2D prefix sum).* =S[x,y]= = sum of everything strictly
above-left of =(x,y)=; built in one pass with inclusion–exclusion, after
which any rectangle sum is four lookups:

#+begin_example
build:  S[x,y] = S[x-1,y] + S[x,y-1] - S[x-1,y-1] + grid[x-1,y-1]
query:  sum(x1..x2, y1..y2) = S[x2+1,y2+1] - S[x1,y2+1] - S[x2+1,y1] + S[x1,y1]
#+end_example

Marking "outside" as 1 turns "rectangle lies fully inside" into "rectangle
sum is 0" — an O(1) test per candidate pair.

** Hash table as a visited set; BFS by levels

- *Visited set*: =(puthash key t table)= / =(gethash key table)=.
  [[file:AoC2025/src_lisp/puz_07.el][2025 puz_07]] part 1 uses exactly the same table type as part 2, once as
  a visited set (count each splitter once) and once as a memo cache
  (count paths) — the same DFS, the only difference is what is stored.
- *Test function*: =eql= is the default and the right one for integer keys
  (positions, bitmasks); =equal= only when keys are strings or lists.
  Integer-encoded state is the cheap option.
- *BFS without a queue* ([[file:AoC2025/src_lisp/puz_10.el][2025 puz_10]]): keep the whole frontier as a list,
  and build the next frontier with nested =cl-loop ... append=. The number
  of rounds is the distance. No =popleft= needed — lists have no cheap one
  anyway (=(pop q)= is fine, appending at the tail is O(n)).

#+begin_src emacs-lisp
(setq frontier
      (cl-loop for state in frontier
               append (cl-loop for move in moves
                               for new = (logxor state move)
                               unless (gethash new seen)
                               do (puthash new t seen) and collect new)))
#+end_src

* Data types and sequences

Overview from a learning session on why both =seq-intersection= and
=cl-intersection= exist. Focus on sequences.

** Type tree

#+begin_example
object
├── atoms
│   ├── numbers: integer (fixnum / bignum), float
│   ├── symbol   (nil, t, keywords like :test are all symbols)
│   └── ...      buffer, marker, process, window, hash-table, record, closure ...
└── sequence
    ├── list     = nil  |  cons cell whose cdr is a list
    └── array
        ├── vector       [1 "a" foo]   any element type
        ├── string       "abc"         elements are characters
        ├── bool-vector
        └── char-table
#+end_example

=sequence= and =array= are abstract categories with predicates
(=sequencep=, =arrayp=), not things you construct. Concrete types are
list, vector, string. Check anything with =type-of= or =cl-typep=.

** The three sequence types

|                | List                          | Vector               | String                    |
|----------------+-------------------------------+----------------------+---------------------------|
| Structure      | chain of cons cells           | contiguous block     | contiguous block of chars |
| Element access | =nth= / =elt=, O(n)           | =aref= / =elt=, O(1) | =aref= / =elt=, O(1)*     |
| Length         | O(n), walks the chain         | O(1)                 | O(1)                      |
| Grow           | O(1) =cons= / =push= at front | fixed, copy to grow  | fixed, copy to grow       |
| Literal        | ='(1 2 3)=                    | =[1 2 3]=            | ="abc"=                   |
| Elements       | anything                      | anything             | characters only           |

* Multibyte strings complicate =aref= internally, but Emacs caches
positions; treat it as O(1) in practice.

Things to keep straight:
- *Characters are integers.* =?a= is 97. No separate char type, hence
  =(- ?C ?A)= → 2, and =(aref "abc" 0)= → 97.
- *nil is three things:* the empty list, false, and a symbol.
  =(listp nil)= → t, =(consp nil)= → nil.
- *Lists are a convention on cons cells.* Alists and plists are shaped
  lists, not types. =(a . b)= is a cons but not a proper list.
- *Literals are constants.* ='(...)=, =[...]= and ="..."= in source may
  be shared — never mutate them.

** Three API layers (why there is overlap)

*** C primitives
=length=, =elt=, =nth=, =aref=, =mapcar=, =mapconcat=, =append=,
=concat=, =vconcat=, =reverse=, =sort=, =member=, =memq=.
Fast, already polymorphic where sensible. =mapcar= takes any sequence
and always returns a list.

*** cl-lib — Common Lisp emulation
Follows the CL spec and inherits its choices:
- =cl-intersection=, =cl-union=, =cl-set-difference= are *list-only*
  (CL defines set functions on lists). A string errors.
- Default equality =eql=; override with =:test #'equal= etc.
- Result order of set functions is unspecified.
- Other reasons to load it: =cl-loop=, =cl-defstruct=, =cl-count=,
  destructuring.

*** seq.el — native Emacs, generic functions
Built on =cl-defgeneric=:
- Works on *any sequence type*; extensible with new methods.
- Default equality =equal=, as an optional positional argument (not a
  keyword).
- Most functions return a *list* regardless of input: =seq-filter=,
  =seq-map=, =seq-intersection=, =seq-uniq=. Some preserve the type:
  =seq-subseq=, =seq-reverse=. Convert with =seq-into=.
- =seq-intersection= keeps the order of its first argument.

Example: =(seq-intersection "abcd" "cxa")= works directly on strings
and returns a list of characters (integers). =cl-intersection= would
need =string-to-list= first.

** Equality

| Predicate | True when                               | Use for                            |
|-----------+-----------------------------------------+------------------------------------|
| =eq=      | same object                             | symbols, fixnums (chars), identity |
| =eql=     | =eq=, or numbers of same type and value | numbers incl. floats / bignums     |
| =equal=   | same structure and contents             | strings, lists,  vectors           |
| ~=~       | numerically equal (=(= 1 1.0)= → t)     | numbers only, errors otherwise     |

Function pairs follow these: =memq= / =member=, =assq= / =assoc=,
=delq= / =delete=. The =q= versions use =eq=.

Chars are fixnums, so =eq=, =eql= and =equal= agree on them — the
cl (=eql=) vs seq (=equal=) default doesn't matter for chars. It does
matter once elements are strings or lists.

** Rule of thumb

- =seq-*= when the input might not be a list, or for one consistent API.
- =cl-*= for CL semantics and keyword args (=:test=, =:key=), and for
  =cl-loop= and friends.
- Primitives in hot loops, where they are fastest.




* Mutation, places and cells

** Two kinds of write

| Kind      | How                      | Who sees it                          |
|-----------+--------------------------+--------------------------------------|
| Rebinding | =setq=, =(push x var)=       | only that variable                   |
| Mutation  | =setcar=, =setcdr=, =aset=     | everyone holding a reference to the object |

=setf= is sugar that picks one of these. You can't always see which:
=(setf (alist-get k al) v)= mutates if =k= exists (=setcdr= on the cell),
but *rebinds* =al= if it doesn't (pushes a new cell onto the variable).

Python analogy: =sub.append(x)= mutates, =sub = sub + [x]= rebinds.

** Places (generalized variables)

=push=, =pop=, =setf=, =cl-incf= work on any form =setf= knows how to
write: =(nth i xs)=, =(aref v i)=, =(car x)=, =(cdr x)=, =(gethash k h)=,
=(alist-get k al)=. =setf= looks at the *form*, it doesn't evaluate it —
a call to your own function is not a place.

=(push x (cdr cell))= expands to =(setcdr cell (cons x (cdr cell)))=:
a real mutation of =cell=. Check with =pp-macroexpand-last-sexp=.

Escape hatch for "pointer to a place": =gv-ref= / =gv-deref=.

** Hold the cell, not the value

To modify something inside a nested structure, hold an object that
*lives in* the structure and mutate it.
- =(assoc k al)= → the =(k . v)= cell, mutate its cdr.
- =(alist-get k al)= → just the value; pushing onto it changes nothing.
- An empty entry: =(cons "name" nil)=, prints as =("name")=.
- The root needs a cell too: =(list (cons "/" nil))=.

Test: =(eq var (assoc "dir" parent))= → =t= if you hold the cell.

* Recursion with an accumulator: =let= + =cl-labels=

#+begin_src emacs-lisp :eval no
(defun collect-things (root)
  (let ((acc nil))                       ; fresh per call, not global
    (cl-labels ((walk (node)
                  ;; recurse with (walk child)
                  ;; (push something acc) as side effect
                  ;; return the value the recursion needs
                  ))
      (walk root))
    acc))
#+end_src

- =cl-labels=, not =cl-flet= — only =cl-labels= lets the function call itself.
- Compute → store → return: =push= returns the *list*, so the value the
  recursion needs must be the last form.
- A =let= with no body returns =nil=.
- Needs =lexical-binding: t=.

* Folds

- The step function is called as =(fn ACC ELEM)= — accumulator first.
- State belongs in the accumulator; a lambda that needs to "remember"
  is a sign the state is in the wrong place.
- =seq-reduce=: =(fn seq initial)=, initial required.
- =cl-reduce=: initial optional (=:initial-value=); without it the first
  element seeds the fold.
- Writing =(f (f a b) c)= by hand → it's a fold. N-way intersection:
  fold =seq-intersection=.

=let= inside a lambda is fresh on every call. =let= *around* a lambda
persists between calls (let over lambda). Beware =(let ((x '(0))) ...)=:
the quoted literal is shared, so mutating it persists anyway.

* cl-loop reminders

| Clause                        | Meaning                                       |
|-------------------------------+-----------------------------------------------|
| =for x in list=                 | elements                                      |
| =for x on list=                 | successive *tails*                            |
| =for c across string=           | elements of a string or vector                |
| =for x being the elements of s= | any sequence                                  |
| =with v = expr=                 | bind once before the loop                     |
| =for x = init then expr=        | running state                                 |
| =thereis expr=                  | stop at first non-nil, return it              |
| =do f1 f2=                      | several forms ok (indentation is poor → =progn=) |
| =finally return x=              | =finally= alone does *not* set the return value |

Destructuring is tree-shaped: =for ((a1 a2) (b1 b2)) = ...=.

* Sets

No set type: sets are lists with set operations (O(n·m)).
- Fast: hash table with =t= values (=:test 'equal= for strings / lists;
  lists work fine as keys).
- Small fixed universe: bit set in an integer — =logand= ∩,
  =logior= ∪, =logcount= size, =logb= position of a single bit.
- =delete-dups= is hash-based but destructive.

* Lookups with string keys

| Function       | Default test                      |
|----------------+-----------------------------------|
| =assq=           | =eq=                                |
| =assoc=          | =equal=                             |
| =alist-get=      | =eq= — pass =nil nil #'equal= for strings |
| =assoc-string=   | case-fold option, symbols by name, bare elements |

=assoc= skips non-cons elements silently — a list of plain strings is
not an alist.

* Debugging

- =(message "%S : %s" x (type-of x))= — =%S= shows ="12"= vs =12=.
- =%s= for humans, =%S= for debugging.
- =(wrong-type-argument number-or-marker-p nil)= → =+= / =sum= got
  =nil=: some branch returned nothing.

* Lisp-1 vs Lisp-2

Elisp and CL are Lisp-2: a symbol has a value cell and a function cell,
hence =#'= and =funcall=. Scheme is a Lisp-1: one namespace, =(f x)= works
on a function held in a variable. Not about code-as-data — all Lisps
are equally homoiconic.
